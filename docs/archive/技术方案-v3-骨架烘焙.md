> 引擎：**Godot 4.7.2**（`F:\Godot\Godot_v4.7.2-stable_win64.exe`）

## 修订说明：v2 → v3（当前版本）

| 项 | v2（骨骼运行时） | v3（骨架烘焙 + 帧表运行时） |
|---|---|---|
| 运行时动画载体 | Bone2D 关键帧实时变形 | 8 方向 × N 帧图集，帧号驱动 |
| 与参考视频一致度 | 组合层一致，动画层不一致 | **10 项全一致**（见 §12） |
| 运行时依赖 | `Skeleton2D` / `Bone2D` | 一个时钟 + N 个 `Sprite2D` |
| 蒙皮 | 必须真蒙皮（Godot 手工涂权重） | **不需要**（弯曲在烘焙期由骨骼算好） |
| 换装成本 | 换贴图 | 换图集 |
| 加动作成本 | 调骨骼曲线 | 调骨骼曲线 + 重烘 90 秒 |

**为什么再改一次**：v2 的运行时是骨骼驱动，和参考视频的帧表算法不一致。用户要求“和视频里面一致就行”。

v3 把两者拆开了：**骨架继续当生产工具**（它解决的是「230 个部件怎么对齐」这个真实问题），**运行时退回帧表**（它解决的是「和参考实现一致 + 不依赖 Godot 那套难用的蒙皮工具」）。

代价只有一个：动作改完要重烘。实测一轮 **90 秒 / 11 个部件 / 4 动作**，可接受。

| 项 | v1（帧动画纸娃娃） | v2（骨骼装配） |

## 4. 角色装配系统（核心，占总工作量 55%）

### 4.1 关键设计：能挂就不蒙

Godot 的 2D 蒙皮工作流（Polygon2D + 逐点涂权重）很原始：**没有笔刷权重、没有自动权重**，官方改进提案至今未合入。如果 234 个部件 × 5 视图都要涂权重，这个项目会死在蒙皮上。

所以第一条架构原则：

> **每个部件都挂成 Bone2D 的子节点，用节点继承变换，不用蒙皮。**

Bone2D 旋转 → 子节点跟着转。这就是经典的 **Cutout（剪纸）动画**，Spine 里也是这个思路。

| 部件类型 | 实现方式 | 权重工作量 |
|---|---|---|
| 帽子、武器、鞋、耳饰、面饰、肩甲、饰品 | `Sprite2D` 直接做 `Bone2D` 子节点 | **0** |
| 头、头发（短）、躯干、衣服分片、四肢分片 | 切成 2~6 片，每片做 `Bone2D` 子节点 | **0** |
| 披风、长发、尾巴 | `Polygon2D` + `skeleton` + 权重（骨链 2~3 段） | 少量，约 5 个部件 |

**结论：真正需要蒙皮的部件 ≤ 5 个，其余全部零成本。** 这直接绕开了 Godot 的最大短板。

代价：Cutout 的弯曲处会出现“缝”（两片之间露底）。解法是**关节遮盖**——在关节处多画 2~3px 被遮住的肉/布料，转动时相互覆盖。这是 2D 动画的行业标准做法，见 §4.8。

### 4.2 骨架规格（20 骨）

坐标系：256×256 画布，原点左上，(128, 216) 为脚底中心。

```
hip (128,150)                        ← 根骨
├─ spine (128,130)
│  └─ chest (128,112)
│     ├─ head (128,78)
│     ├─ arm_l (110,108)             ← 肩
│     │  └─ fore_l (98,128)          ← 肘
│     │     └─ hand_l (92,148)       ← 腕
│     ├─ arm_r (146,108)
│     │  └─ fore_r (158,128)
│     │     └─ hand_r (164,148)
│     └─ cape_1 (128,105)            ← 骨链，真蒙皮
│        └─ cape_2 (128,140)
├─ thigh_l (116,158)
│  └─ shin_l (114,186)
│     └─ foot_l (114,208)
└─ thigh_r (140,158)
   └─ shin_r (142,186)
      └─ foot_r (142,208)
```

**骨骼索引陷阱（务必记住）**：`Skeleton2D` 里骨骼的索引是**层级前序遍历顺序**，不是创建顺序。脚本里必须用 `Bone2D.get_index_in_skeleton()` 取真实索引。上图的遍历序为：

```
0 hip   1 spine   2 chest   3 head   4 arm_l  5 fore_l  6 hand_l
7 arm_r 8 fore_r  9 hand_r  10 thigh_l 11 shin_l 12 foot_l
13 thigh_r 14 shin_r 15 foot_r 16 cape_1 17 cape_2
```

其他必须遵守的约束：

- 增删骨骼后必须 **Overwrite Rest Pose**，否则动画参考姿态全错
- `Bone2D` 长度不能为 0，否则变换矩阵退化，报 `Condition 'det == 0'`
- 动画只给 `Bone2D` 打关键帧，**绝不给部件节点打**

### 4.3 Cutout 分片规范

不是所有部件都要切。分片数由“这个部件在动画中需要弯几次”决定：

| 槽位 | 分片数 | 分片方式 |
|---|---|---|
| `body` | 6 | 躯干 / 上臂L,R / 前臂L,R / 腿 |
| `head` | 1 | 整块绑 head 骨 |
| `hair_front` | 1 | 整块绑 head 骨 |
| `hair_back` | 1~2 | 长发的下半段单独一片绑摆动骨 |
| `clothes` | 1~6 | 短衣 1 片；长袍拆 躯干/下摆/袖×2 |
| `cape` | 1 | **Polygon2D 蒙皮**，绑 cape_1/cape_2 |
| `shoes` | 1 | 绑 foot_l / foot_r（按视图取） |
| `weapon` | 1~2 | 剑身+剑柄可合一，整块绑 hand_r |
| 其余 9 槽 | 1 | 整块，绑各自骨骼 |

**分片绘制要求**：同一部件的所有分片画在**同一张 256×256 画布**上、处于**同一 rest 姿势**。程序按分片的多边形蒙版切分，不手工对齐——这样切片的相对位置天然正确。

### 4.5 视图集：画 5 张，运行时用 8 列

骨架只能在平面内变形，**解决不了“转向”**——正面和侧面是两套完全不同的画。方向仍然要多套美术。

v3 的做法：**美术只画 5 套视图，烘焙时镜像补满 8 个方向，产物是 8 列图集**。

| 目标方向 | S | SW | W | NW | N | NE | E | SE |
|---|---|---|---|---|---|---|---|---|
| 烘焙取自 | s | sw | w | nw | n | **nw 镜像** | **w 镜像** | **sw 镜像** |

- 镜像发生在**烘焙期**（`rig.scale.x = -1` 单独渲染一列），运行时不做任何 `flip_h`
- 运行时切方向 = 改图集列偏移（`frame = 帧号 × 8 + 方向`），零额外开销
- 非对称部件（单手持剑、斜挎包）镜像会翻手 → 这类部件必须画满 8 列，标记 `full8`
- 对称部件（身体、衣服、发型、腿）画 5 套即可，省 37.5% 绘制量

**“4 动作 × 8 方向”的乘法在烘焙期兑现**：每个部件 32 组帧序列，全部由同一套骨骼曲线导出，运行时它们是同一张图集的不同列——不存在“32 套动画”的维护负担，调姿势只改一份关键帧表。

### 4.6 装配：偏移怎么算

部件是骨骼的子节点，但美术是按 256×256 整体画布画的。所以要把“画布坐标”换算成“骨骼局部坐标”：

```
part_local_offset = 画布原点对应的全局位置 - 骨骼 rest 全局位置
                  = Vector2(-128, -216) - bone.rest_global_position
```

（因为画布锚点 (128,216) 对应角色脚底，而角色根节点就在脚底。）

程序化装配时一次性算好，不用手工摆 234 个 Sprite2D。

### 4.7 动画：离线烘焙，运行时回放

骨架只负责“摆出姿势”，帧表负责“播放”，两者通过烘焙脚本交接。

| 动作 | 帧数 | fps | 循环 | 关键骨骼 |
|---|---|---|---|---|
| `idle` | 6 | 6 | 是 | hip 起伏 1.5px、chest 微呼吸、head 微晃 |
| `walk` | 8 | 10 | 是 | thigh/shin 交替、arm 反摆、hip 上下 3px |
| `attack` | 6 | 14 | 否 | arm_r→fore_r 挥出、chest 前倾，播完回 idle |
| `hurt` | 4 | 8 | 否 | chest 后仰、head 后甩、arm 抬起 |

**摆动幅度必须按视图收敛**：侧视 W = 100%，斜向 SW/NW = 80%，正/背视 S/N = 35%。正背面做大幅前后摆动会看起来像“横着走”。

**唯一的双写常量**：`FrameDoll.ACTIONS` 的 fps 与 `tools/bake_frames.gd` 的 `ACTIONS` 必须一致，改一处要同步另一处。

**位移不进动画**：`walk` 是原地循环，位移交给 `CharacterBody2D`，否则会滑步。

### 4.8 关节遮盖（Cutout 的命门）

转动时两片之间露缝是 Cutout 的必然结果。三个手段：

1. **多画 2~3px 隐藏覆盖**：肘、膝、肩、颈的接缝处，两片各自往外多画一点“被遮住的肉/布”，转动时互相盖住
2. **圆形关节垫片**：在肘/膝位置加一个小圆片（同肤色/布色），绑在前一段骨上，作为补缝层，z 夹在两片之间
3. **限制转角**：动画里给关节设旋转上限（肘 ±120°、膝 ±90°），超出必然露缝

验收方式：录一段把手臂举到最高、膝盖弯到极限的极端姿势，逐帧看有没有缝。**先修遮盖，再修权重**——大部分缝不是权重问题，是画的时候没留覆盖。

### 4.9 换色（复用 v1 着色器）

`shaders/part_tint.gdshader` 可直接用在 `Sprite2D` 和 `Polygon2D` 上（都是 canvas_item）。遮罩通道约定不变：R=可染色，G=皮肤区。

关键收益：`skin_tint` 统一驱动脸和手的皮肤色，蓝皮肤角色不会出现“脸蓝手肉色”。

### 4.10 次级动画（披风、长发）

这是唯一用真蒙皮的地方。做法：

- `Polygon2D` 沿长度方向细分 6~10 个顶点，`skeleton` 指向骨架
- 权重按 UV.y 线性分配给 `cape_1` / `cape_2`
- 动画只转 `cape_1`、`cape_2` 两根骨，用正弦曲线
- 风力强度由 `WeatherDirector` 广播（晴 0.15 / 雨 0.5 / 雪 0.25）

**替代方案（更省）**：不做蒙皮，直接把披风切成 3 段刚片，每段绑一根骨，靠遮盖缝合。效果略硬，但零蒙皮。先用这个，效果不够再上蒙皮。

## 5. 世界模拟

### 5.1 时间系统

```gdscript
# autoload/game_clock.gd
extends Node

signal minute_changed(total_minute: int)
signal hour_changed(hour: int)
signal day_changed(day: int)
signal season_changed(season: int)

const MIN_PER_DAY := 1440
const DAYS_PER_SEASON := 28

@export var real_seconds_per_game_day: float = 900.0   # 15 分钟 1 天

var total_minute: int = 6 * 60
var _acc: float = 0.0

func _process(delta: float) -> void:
    _acc += delta * (MIN_PER_DAY / real_seconds_per_game_day)
    if _acc < 1.0:
        return
    var step := int(_acc)
    _acc -= step
    var prev_hour := hour()
    var prev_day := day()
    total_minute += step
    if hour() != prev_hour:
        hour_changed.emit(hour())
    if day() != prev_day:
        day_changed.emit(day())
        if day() % DAYS_PER_SEASON == 0:
            season_changed.emit(season())

func hour() -> int: return (total_minute / 60) % 24
func day() -> int: return total_minute / MIN_PER_DAY
func season() -> int: return (day() / DAYS_PER_SEASON) % 4
func time_of_day_01() -> float: return float(total_minute % MIN_PER_DAY) / MIN_PER_DAY
```

`total_minute` 是唯一状态，其余是纯函数派生。存档只存一个 int，读档重放信号恢复。

### 5.2 昼夜

`GradientTexture1D` 存 24 小时色调曲线，每帧采样写入 `CanvasModulate.color`。夜晚压到 0.35 再靠 `PointLight2D` 提亮——重点是做**光比**，不是单纯变暗。

### 5.3 天气

状态机 + 权重转移表，切换间隔 5~15 游戏分钟。输出 `EnvironmentParams`：

| 参数 | 消费方 |
|---|---|
| `light_mul` | 昼夜控制器 |
| `wind_strength` | 披风/长发骨链、粒子 |
| `wetness` | 火焰点燃概率↓、植物生长↑ |
| `temperature_offset` | 结冰判定 |

### 5.4 四季

**不要全屏 hue-rotate**（会把角色一起染绿）。用图集变体按需换源：

```gdscript
func set_season(s: int) -> void:
    for src_id in tilemap.tile_set.get_source_count():
        var src := tilemap.tile_set.get_source(src_id) as TileSetAtlasSource
        if src and src.resource_name.begins_with("foliage"):
            src.texture = SEASON_ATLASES[s]
```

落叶树/草地/花换 4 套（约 3 张 2048² 图集），石头建筑不换。换季加 1.5s 白闪过渡掩盖跳变。

### 5.5 环境互动（火 / 水 / 温度）

格子状态 + **活跃集**，不在每帧遍历全图：

```gdscript
class_name CellState extends RefCounted
var wet: float = 0.0
var burning: float = 0.0
var frozen: bool = false
var flammable: float = 0.0
```

```gdscript
const TICK_HZ := 4.0
var _active: Dictionary = {}      # 只有状态在变的格子才进队

func _process(delta: float) -> void:
    _acc += delta
    if _acc < 1.0 / TICK_HZ: return
    _acc = 0.0
    var next_active := {}
    for pos in _active.keys():
        _step_cell(pos, next_active)
    _active = next_active

func _step_cell(pos: Vector2i, next_active: Dictionary) -> void:
    var c := get_cell(pos)
    if c == null: return
    if c.burning > 0.0:
        c.burning += 0.35 / TICK_HZ
        if randf() < c.flammable * (1.0 - c.wet) * 0.6 / TICK_HZ:
            for n in NEIGHBORS:
                var nc := get_cell(pos + n)
                if nc and nc.burning == 0.0 and nc.flammable > 0.0:
                    ignite(pos + n)
        if c.burning >= 1.0:
            _char(pos)                  # 焦黑地块，N 天后重生
    if c.burning > 0.0 or c.wet > 0.0 or c.frozen:
        _activate(pos, next_active)
```

1000×1000 地图，雨天全场湿润时活跃格也不过几千个。

### 5.6 多阶段建筑

`Building` 持有 `Array[BuildingStage]`（地基→框架→墙体→屋顶→装饰），每阶段 = 贴图 + 碰撞 + 交互点。玩家敲击累加 `progress`，满则切下一阶段；中间用 `mix(transparent, opaque, progress)` 着色器做“逐渐显影”。

## 6. 美术生产管线（纯 2D，无 3D）

### 6.1 对齐靠什么

没有 3D 的构造性对齐，靠**骨架 rest pose + 统一画布**：

> 所有部件都画在同一张 256×256 画布、同一 rest 姿势、同一锚点。
> 装配时程序按 `画布坐标 - 骨骼rest坐标` 换算偏移，对齐是**计算出来的**，不是摆出来的。

这比 v1 的“底图描线”更硬——v1 靠人眼对齐，v2 靠坐标计算。**只要画布和锚点一致，就绝不会错位。**

### 6.2 标准底图（Base Sheet）

仍然是第一优先级资产，作用是“所有分片的共同基准”：

| 项 | 要求 |
|---|---|
| 内容 | body 的 5 个视图各 1 张 rest 姿势（s/sw/w/nw/n） |
| 画布 | 256×256，锚点 (128,216) |
| 关节标记 | 8 个关节点高饱和标色，与 §4.2 坐标表一致 |
| 产出 | `assets/base/base_{view}.png` + `base_joints.json` |
| 纪律 | 锁定后改需评审；改底图 = 全部部件重新对位 |

### 6.3 生产流程

```
① 画底图（5 视图 rest 姿势）→ ② 逐部件绘制（同画布、同姿势）
   → ③ 切分片（按槽位规范切 1~6 片）→ ④ 装配（脚本生成 Sprite2D 树）
   → ⑤ 校验（尺寸/命名/锚点）→ ⑥ 动画（调骨骼曲线，只做一次/视图）
```

**关键：③ 切分片在 ④ 之前用程序完成**——按多边形蒙版裁切，切片相对位置天然正确，不需要像 v1 那样逐帧对齐。

### 6.4 AI 的定位

| 用途 | 可行性 | 纪律 |
|---|---|---|
| 部件整图生成 | 高 | 必须 img2img，底图作初始图，denoise ≤ 0.4 |
| 5 视图一致性 | **低** | AI 很难保证同一部件 5 个角度一致，建议人画或 AI 出主体后人工改角度 |
| 材质纹理 | 高 | 生成纹理后按部件轮廓裁切 |

**红线**：denoise > 0.5 会改形体，视图之间就对不上。这条底线在 v2 里更严格，因为视图必须能叠在同一骨架上。

### 6.5 成本重算

假设：全重绘 30 min/视图，切分片 15 min/部件，动画 1.5 h/动作·视图。

| 部件类 | 变体 | 视图 | 单件工时 | 小计 |
|---|---|---|---|---|
| body（含底图） | 4 | 5 | 3.5 h | 14 h |
| head | 11 | 5 | 2.0 h | 22 h |
| hair（前后） | 34 | 5 | 2.0 h | 68 h |
| clothes | 29 | 5 | 3.5 h | 101 h |
| hat | 23 | 5 | 1.5 h | 34 h |
| weapon | 33 | 5 | 1.5 h | 50 h |
| 其余 10 槽 | ~80 | 5 | 1.5 h | 120 h |
| 动画 | 20 套 | — | 1.5 h | 30 h |
| 骨架搭建 + 装配脚本 | — | — | — | 25 h |
| **合计** | **~234** | — | — | **≈464 h** |

对比 v1 帧动画的真实成本（按同样假设重算）：234 部件 × (5 视图全绘 + 95 帧增量) ≈ **1,050 h**。

**骨骼方案省 55%，且动作数越多优势越大**——v1 加一个动作 = 每个部件补画 5 张；v2 加一个动作 = 调 5 套骨骼曲线。

## 8. 性能预算

### 8.1 目标

| 指标 | 目标 |
|---|---|
| 帧率 | 60fps @1920×1080 |
| 同屏骨骼角色 | 40 |
| 每角色节点数 | ≤30（20 骨 + 部件片） |
| Draw Call | ≤120 |

### 8.2 优化手段

1. **图集打包**：同一槽位的所有变体打进一张图集，40 角色 × 30 节点合批后 draw call 压到个位数
2. **骨架降频**：视野外 NPC 关掉 `AnimationPlayer`，只做位移插值
3. **`Skeleton2D` 不需要每帧刷新**：静态 NPC（站立不动）的骨骼只在动画关键帧变化，用 `AnimationPlayer` 的 `callback_mode_discrete` 或直接停播
4. **per-instance uniform** 做换色参数，避免 800 个独立材质破坏合批
5. **对象池**：NPC 进出示视野复用节点

### 8.3 已知陷阱

| 陷阱 | 症状 | 规避 |
|---|---|---|
| 骨骼索引按创建顺序取 | 动画/权重作用到错骨骼 | 一律用 `get_index_in_skeleton()` |
| 加骨骼没重设 rest pose | 动画姿态全歪 | 改骨架后 Overwrite Rest Pose |
| Bone2D 长度 0 | `det == 0` 警告 | 每根骨给非零长度 |
| 给 Polygon2D 打关键帧 | 动画被覆盖、部件飞走 | 只给 Bone2D 打 |
| 无权重时 Polygon2D 消失 | 什么都不显示 | 先 Fill 铺权重再细调 |
| walk 动画里带位移 | 滑步 | 位移交给 CharacterBody2D |

| 6 | 组合数 | 乘法组合，画面给出 44,552,959,642,863 | 槽位 → 部件的乘法表 | 一致 |
| 7 | **动画驱动** | **同一帧表：帧号 n → 每槽取第 n 帧** | **`frame = 帧号 × 8 + 方向`，单时钟广播** | **一致（v3 起）** |

| 9 | 次级动画 | 头发、披风被风吹起来 | `cape_1/2` 骨骼摆动烘进帧 | 一致 |

这也是这套方案真正的价值：参考作者最容易出错的环节（230 个部件 × 32 组帧的对齐）在这里被工具吃掉了，而运行时的算法和观感与他完全同一套。

## 13. 烘焙管线（v3 新增工序）

### 13.1 输入与输出

| 项 | 规格 |
|---|---|
| 输入 | `assets/parts/{slot}/{stem}_{s,sw,w,nw,n}.png`，256×256，锚点 (128,216) |
| 输出 | `assets/frames/{slot}/{stem}_{action}.png`，宽 **2048**（8 方向 × 256），高 = 帧数 × 256 |
| 工具 | `tools/bake_frames.gd` + `tools/bake_frames.tscn` |
| 命令 | `godot --path . res://tools/bake_frames.tscn` |

### 13.2 帧索引（运行时唯一要记的公式)

```
frame = 行 × 8 + 列 = 帧号 × 8 + 方向
```

列 = 方向（S/SW/W/NW/N/NE/E/SE），行 = 帧。`hframes = 8`，`vframes = 帧数`。

### 13.3 五个实测踩到的坑

1. `SubViewport` 必须 `transparent_bg = true` 且 `render_target_update_mode = UPDATE_ALWAYS`，否则出全黑图
2. 烘焙台上骨架节点要 `position = +CANVAS_ANCHOR`：运行时内容坐标是「画布 − 锚点」，烘焙时要加回来，画布才铺满 256 视口
3. 逐部件单独出图必须做隔离（`solo_slot()`），且渲染前 `await RenderingServer.frame_post_draw`，否则拿到上一帧
4. 图集用 `Image.blit_rect` 拼；一张 2048×2048 约 16MB，按「部件 → 动作」顺序落盘，避免 44 张同时驻留内存
5. `set_direction(0)` 有「方向未变」早退分支，首次烘焙前要手动 `refresh()`，否则第 0 帧拿到的是未应用的视图

### 13.4 实测成本

11 个部件 × (6+8+6+4) 帧 × 8 方向 = **2,112 次渲染，约 90 秒**。

按 234 个部件外推约 **32 分钟**——一次性成本，且只在骨架或姿势变更时才需要重跑。

### 13.5 尚未做

**遮罩烘焙**：当前图集整块可染，所以“手跟着脸变色”在烘焙管线里还没有落地。要做的话，把 mask 源图按同一条管线渲成同尺寸图集（R=可染区、G=皮肤区），挂到 `FramePart.tint_mask` 即可，shader 不用改。

## 14. 生产与运行的分工

| 环节 | 谁负责 | 说明 |
|---|---|---|
| 部件对齐 | 骨架 | 所有部件绑同一骨架，姿势一改全部同步 |
| 姿势设计 | 骨架 | 一份关键帧表，导出 8 个方向 |
| 运行时播放 | 帧表 | 单时钟 + N 个 `Sprite2D` |
| 换装 | 帧表 | 换图集，完全不碰骨架 |
| 性能 | 帧表 | 无骨骼计算、无蒙皮，40+ 同屏没有压力 |

**冻结策略**：骨架在 M1 定稿后冻结，之后原则上只改贴图与换色。若必须改形体，重跑烘焙（90 秒）并抽查 3 个方向的行走帧是否仍然对齐。
