## 1. 目标与复刻边界

### 1.1 要复刻的核心能力

| 能力 | 参考视频中的表现 | 本项目目标 |
|---|---|---|
| 纸娃娃组装 | 17 槽位、最多 20 层，16 个角色共用 1 个基础木头人 | 同构实现，槽位可配置扩展 |
| 动画自动跟随 | 8 方向 × 待机/行走/攻击/受击，换装不用重画动作 | 帧表驱动，部件零重画 |
| 部件独立换色 | 每部件单独调色，"画一件衣服等于白送十件" | HSV 偏移 + 皮肤遮罩双通道 |
| 组合爆炸 | 11×17×23×29×9×33×14×17×12×…×4 ≈ 4.45e13 | 同量级，并做"丑组合"治理 |
| 次级动画 | 头发、披风被风吹动 | 顶点着色器风力摆动 |
| 世界模拟（预告） | 昼夜、天气、四季、树着火、水结冰、多阶段建筑 | 纳入 M2/M3 里程碑 |

### 1.2 明确的非目标（第一期不做）

- 不做联网、不做多语言、不做手柄适配、不做移动端触屏（仅预留）
- 不做战斗中复杂的技能/连招系统（只验证"攻击/受击"两态表现）
- 不做 3D 角色（世界可做 2.5D 分层透视，但角色是纯 2D 精灵）

### 1.3 成功判据

1. 美术只需画出**一套基础体型**的 4 个动作，就能生成 ≥16 个视觉上明显不同的角色
2. 换装、换色实时生效，无需重新烘焙、无卡顿（<2ms/角色）
3. 同屏 40 个 NPC、60fps @1080p 稳定
4. 新增一个部件只需丢 PNG 进目录 + 改一行 JSON，不写代码

## 2. 技术选型

### 2.1 引擎：Godot 4.3+

选它的硬理由（不是"免费"这种泛泛之谈）：

- **2D 是原生一等公民**：Sprite2D 的 `hframes/vframes` 天然支持"一张图切成 8 方向 × N 帧"，纸娃娃的部件同步只要改 `frame` 一个整数
- **图集合批自动**：相同纹理的 Sprite2D 会被自动 batch，20 层 × 40 角色也能压住 draw call
- **`CanvasModulate` + `PointLight2D`** 做昼夜成本极低，不需要后处理
- **Resource 序列化**：`PartDef` 这类数据做成 `.tres`，编辑器里可视化配置，运行时零解析开销
- **GDScript 够用**：这类游戏的瓶颈是精灵合成与 AI 逻辑，不在语言性能；热点（网格传播）用 C# 或 GDExtension 补

**不选 Unity 的原因**：2D 精灵合成需要自己写 Atlas/Animator 同步逻辑，且 AI 生成的散图导入切图流程更繁琐。
**不选 Web 的原因**：后期世界模拟（大面积火/水传播、四季图集切换）在浏览器内存与 GC 上会很难受。

### 2.2 渲染与分辨率

| 项 | 决策 | 说明 |
|---|---|---|
| 渲染器 | Forward+ | 需要 2D 光照与法线 |
| 基准分辨率 | 1920×1080 | 参考视频是 1080p |
| 缩放模式 | `canvas_items` + `expand` | 窗口任意拉伸不变形 |
| 角色单元格 | 256×256 px | 部件画布统一尺寸，见 §4.1 |
| 纹理过滤 | Nearest（像素）/ Linear（高清矢量风） | 本项目走高清矢量风 → Linear + Mipmap 关 |

> **关键决策：美术风格选"高清矢量 Q 版"而非像素风。**
> 原因：AI 生成像素风的一致性极难控制（像素网格对齐、调色板受限），而高清矢量风 AI 出图质量稳定，8 方向重绘的容错空间也更大。

```
            │ 信号：minute/day/season_changed, weather_changed
┌───────────▼──────────────┐   ┌──────────────────────────┐
│  表现层 Rendering         │   │  模拟层 Simulation        │
│  ├ PaperDoll（纸娃娃）    │   │  ├ WorldGrid（格子状态）   │

│  └ DayNightController    │   │  └ BuildingSystem        │
└───────────┬──────────────┘   └──────────┬───────────────┘
            │                             │
┌───────────▼─────────────────────────────▼───────────────┐
```

## 4. 纸娃娃系统（核心，占总工作量 50%）

### 4.1 资产规范（先定死，否则 AI 素材会失控）

**画布规范**

| 项 | 值 | 理由 |
|---|---|---|
| 单帧画布 | 256 × 256 | 容纳武器挥砍的最远伸展 |
| 角色锚点 | (128, 216) | 脚底中心，所有帧对齐此点 |
| 可绘制安全区 | x:32~224, y:16~240 | 超出视为越界，校验脚本会报错 |
| 图层透明 | 必须带 Alpha，禁止白底 | AI 出图常见问题 |

**方向策略：画 5 列，镜像出 8 方向（纯 2D 的关键降本手段）**

纯手绘/半 AI 路线下，方向数直接决定工作量。左右对称的部件不需要画 8 个方向——把左侧方向水平翻转就得到右侧：

| 目标方向 | S | SW | W | NW | N | NE | E | SE |
|---|---|---|---|---|---|---|---|---|
| 取自列 | 0 | 1 | 2 | 3 | 4 | **3 镜像** | **2 镜像** | **1 镜像** |

所以一张图只需要 **5 列**，即可覆盖 8 方向，绘制量降到 62.5%。三种模式按部件性质选：

| mirror_mode | 列数 | 适用部件 | 说明 |
|---|---|---|---|
| `MIRROR5` | 5 | body、head、hair、clothes、cape、hat | 默认。左右对称，镜像无破绽 |
| `MIRROR3` | 3 | 早期原型、非关键部件 | 只画 S/W/N，E 用 W 镜像。**M1 阶段先用这个** |
| `FULL8` | 8 | weapon、offhand、单侧挂件 | 武器在左手还是右手，镜像会翻手，必须单独画 |

> **注意**：`MIRROR5` 对"单手持剑、斜挎包、独眼眼罩"这类非对称部件不成立。判定规则很简单——**问自己"从正面看是左右对称的吗"**，不是就标 `FULL8`。武器类虽然只占 2 个槽位，但体积小，画 8 列的成本可控。

**序列帧图（Sprite Sheet）布局**

一张 PNG = 1 个部件的 1 个动作，**列 = 方向（5 或 3 或 8），行 = 帧**：

```
         S    SW   W    NW   N          ← 列 = 5（MIRROR5）
帧0   ┌────┬────┬────┬────┬────┐
帧1   │    │    │    │    │    │
帧2   │    │    │    │    │    │
 ...  └────┴────┴────┴────┴────┘
```

- 图宽 = 列数 × 256（5 列 = 1280，3 列 = 768，8 列 = 2048），图高 = 帧数 × 256
- Godot 侧：`hframes = 列数`，`vframes = 帧数`，运行时按 `mirror_mode` 映射列号并设 `flip_h`

**命名规范**

```
assets/parts/{slot}/{slot}_{variant}_{action}.png
assets/parts/{slot}/{slot}_{variant}_{action}_mask.png   # 可选：换色遮罩
例：assets/parts/body/body_mage_01_walk.png
```

`slot` ∈ 17 个槽位 key；`action` ∈ idle / walk / attack / hurt；`variant` 由生产管线自增（`_01`、`_02`…）。列数由 `PartDef.mirror_mode` 决定，**不写进文件名**——否则改策略要批量改名。

### 4.2 槽位表（对齐参考视频的 17 槽 / 20 层）

| # | slot key | 中文 | 层数 | z 基准 | 备注 |
|---|---|---|---|---|---|
| 1 | `hair_back` | 后发 | 1 | 0 | 必须在身体之后 |
| 2 | `cape` | 披风 | 1 | 2 | 参与风力摆动 |
| 3 | `wing` | 翅膀 | 1 | 4 | 参与风力摆动 |
| 4 | `tail` | 尾巴 | 1 | 5 | 参与风力摆动 |
| 5 | `body` | 身体 | 1 | 10 | **基础体型，必选** |
| 6 | `clothes` | 衣服 | 5 | 20~24 | 分 内衬/主体/外套/腰带/装饰 5 层 |
| 7 | `shoes` | 鞋子 | 1 | 25 | |
| 8 | `head` | 头型 | 1 | 30 | **必选，含肤色区域** |
| 9 | `ear` | 耳朵/角饰 | 1 | 31 | |
| 10 | `face` | 面饰 | 1 | 32 | 眼镜、面罩 |
| 11 | `hair_front` | 前发 | 1 | 34 | 压在头上 |
| 12 | `hat` | 帽子 | 1 | 36 | |
| 13 | `shoulder` | 肩甲 | 1 | 40 | |
| 14 | `glove` | 护手 | 1 | 42 | 含肤色区域（手） |
| 15 | `weapon` | 主手武器 | 1 | 50 / 8 | 朝向背面时降到 8（身体之后） |

### 4.3 数据结构

```gdscript
# core/data/part_def.gd
class_name PartDef
extends Resource

## 方向镜像策略：决定这一部件要画几列
enum Mirror { MIRROR3, MIRROR5, FULL8 }

@export var id: StringName                  # "body_mage_01"
@export var slot: StringName                # "body"
@export var display_name: String           # 用于 UI/随机生成日志
@export var layer_offset: int = 0           # 在槽位基础 z 上的偏移（衣服 5 层用）

## 左右对称部件用 MIRROR5（画 5 列出 8 方向），非对称件用 FULL8
@export var mirror_mode: Mirror = Mirror.MIRROR5

## action(StringName) -> Array[Texture2D]，长度 = 列数（3 / 5 / 8）
@export var sheets: Dictionary = {}

## 换色遮罩：R = 可染色区，G = 皮肤区。为空则整图可染
@export var tint_mask: Texture2D

@export_group("朝向")
## 背面朝向时是否降到身体之下
@export var behind_on_back: bool = false

@export_group("兼容性")
@export var tags: Array[StringName] = []    # "armor", "cloth", "ugly"
@export var weight: float = 1.0             # 随机生成权重
@export var incompatible_with: Array[StringName] = []

func col_count() -> int:
    match mirror_mode:
        Mirror.MIRROR3: return 3
        Mirror.MIRROR5: return 5
        _: return 8
```

```gdscript
# core/data/character_visual.gd
class_name CharacterVisual
extends Resource

## slot(StringName) -> PartDef
@export var equipped: Dictionary = {}
## slot(StringName) -> Color（HSV 偏移打包：x=hue, y=sat, z=val）
@export var tints: Dictionary = {}
## 皮肤统一色（脸、手共用），解决"蓝皮肤却戴着肉色手套"
@export var skin_tint: Color = Color(1, 1, 1)
@export var scale_mul: float = 1.0
```

```gdscript
# core/data/anim_table.gd  —— 全局唯一的帧表，所有部件必须遵守
class_name AnimTable
extends Resource

@export var actions: Dictionary = {
    &"idle":   {"frames": 4, "fps": 6.0,  "loop": true},
    &"walk":   {"frames": 8, "fps": 10.0, "loop": true},
    &"attack": {"frames": 6, "fps": 14.0, "loop": false},
    &"hurt":   {"frames": 2, "fps": 8.0,  "loop": false},
}
```

> **帧表是全系统唯一真相源。** 任何部件如果帧数对不上，校验脚本直接拒绝导入——这是纸娃娃系统能否成立的前提。

### 4.4 运行时合成：一个时钟，N 个 Sprite2D

**不要**给每个部件挂 `AnimatedSprite2D`（会各自漂移、各自计时）。
**也不要**把 20 层每帧 `SubViewport` 合成成一张图（每帧 GPU 回读，性能灾难）。

**正确做法**：`PaperDoll` 持有唯一的时间轴，每帧算出 `(action, dir, frame_index)`，广播给所有 `Sprite2D` 层。

```gdscript
# core/paper_doll/paper_doll.gd  —— 完整可运行版本见 scripts/paper_doll.gd
class_name PaperDoll
extends Node2D

signal frame_changed(action: StringName, direction: int, frame: int)

const DIR_COUNT := 8

## 方向 -> (列号, 是否水平镜像)。MIRROR5 只画 5 列出 8 方向
const DIR_MAP_M5 := [
    Vector2i(0, 0), Vector2i(1, 0), Vector2i(2, 0), Vector2i(3, 0),
    Vector2i(4, 0), Vector2i(3, 1), Vector2i(2, 1), Vector2i(1, 1),
]
const DIR_MAP_M3 := [
    Vector2i(0, 0), Vector2i(1, 0), Vector2i(1, 0), Vector2i(1, 0),
    Vector2i(2, 0), Vector2i(1, 1), Vector2i(1, 1), Vector2i(1, 1),
]

@export var anim_table: AnimTable
@export var visual: CharacterVisual:
    set(v):
        visual = v
        if is_inside_tree():
            _rebuild()

var direction: int = 0          # 0=S 1=SW 2=W 3=NW 4=N 5=NE 6=E 7=SE
var action: StringName = &"idle"

var _frame: int = 0
var _acc: float = 0.0
var _layers: Array[Sprite2D] = []
var _last := Vector3i(-1, -1, -1)      # 去重：只在真正变化时写属性


func _process(delta: float) -> void:
    var cfg: Dictionary = anim_table.actions.get(action, {})
    if cfg.is_empty():
        return
    _acc += delta * float(cfg.get("fps", 8.0))
    var total: int = cfg.get("frames", 1)
    while _acc >= 1.0:
        _acc -= 1.0
        if _frame + 1 >= total:
            if cfg.get("loop", true):
                _frame = 0
            else:
                _frame = total - 1
                play(&"idle")           # 非循环动作播完回 idle
                return
        else:
            _frame += 1
    _flush()


func set_direction(d: int) -> void:
    d = wrapi(d, 0, DIR_COUNT)
    if d == direction:
        return
    direction = d
    _apply_z_order()          # 背面朝向会改 z 序，必须重算
    _flush()


func _flush() -> void:
    var key := Vector3i(direction, hash(action), _frame)
    if key == _last:
        return
    _last = key

    for s in _layers:
        var part: PartDef = s.get_meta(&"part")
        var sheets: Array = part.sheets.get(action, [])
        var m := _dir_map(part)[direction]

        # 列数越界 / 纹理缺失 -> 隐藏该层（不崩）
        if sheets.is_empty() or m.x >= sheets.size() or sheets[m.x] == null:
            s.visible = false
            continue
        s.visible = true

        var tex: Texture2D = sheets[m.x]
        if s.texture != tex:
            s.texture = tex
            s.hframes = part.col_count()
            s.vframes = maxi(1, int(tex.get_height() / CANVAS_H))
        s.flip_h = m.y == 1
        if _frame < s.vframes:
            s.frame = _frame

    frame_changed.emit(action, direction, _frame)


func _dir_map(part: PartDef) -> Array:
    match part.mirror_mode:
        PartDef.Mirror.MIRROR3: return DIR_MAP_M3
        PartDef.Mirror.MIRROR5: return DIR_MAP_M5
        _: return []          # FULL8：直接用 identity，见下方 fallback
```

> `FULL8` 时列号就等于方向本身、不镜像，`_dir_map` 返回空数组走 identity 分支即可（实际实现里用 `m = Vector2i(direction, 0)`）。
> 关键点是 **列数由部件自己的 `mirror_mode` 决定，`hframes`/`vframes` 必须随之更新**——这是切换动作时最容易漏的一步，漏了就会显示错帧或花屏。

```gdscript
func _rebuild() -> void:
    for c in get_children():
        if c is Sprite2D:
            c.queue_free()
    _layers.clear()
    if visual == null:
        return

    var parts: Array[PartDef] = []
    for slot in visual.equipped.keys():
        var p: PartDef = visual.equipped[slot]
        if p != null:
            parts.append(p)
    parts.sort_custom(func(a: PartDef, b: PartDef) -> bool:
        return _base_z(a) + a.layer_offset < _base_z(b) + b.layer_offset)

    for part in parts:
        var s := Sprite2D.new()
        s.name = String(part.slot)
        s.hframes = part.col_count()
        s.vframes = 1
        s.centered = false
        s.position = Vector2(-128, -216)     # 画布锚点对齐脚底中心
        s.texture_filter = CanvasItem.TEXTURE_FILTER_LINEAR
        s.set_meta(&"part", part)
        s.material = _make_material(part, part.slot)
        add_child(s)
        _layers.append(s)

    _apply_z_order()
    _flush()
```

**z 序应用**

```gdscript
const SLOT_Z := {
    &"mount": -10, &"hair_back": 0, &"cape": 2, &"wing": 4, &"tail": 5,
    &"body": 10, &"clothes": 20, &"shoes": 25, &"head": 30, &"ear": 31,
    &"face": 32, &"hair_front": 34, &"hat": 36, &"shoulder": 40,
    &"glove": 42, &"offhand": 48, &"weapon": 50, &"summon": 60,
}

func _base_z(p: PartDef) -> int:
    var z: int = SLOT_Z.get(p.slot, 10)
    if p.behind_on_back and direction in [3, 4, 5]:
        return 8      # 背面朝向：武器/副手沉到身体之下
    return z

func _apply_z_order() -> void:
    for s in _layers:
        var part: PartDef = s.get_meta(&"part")
        s.z_index = _base_z(part) + part.layer_offset
        s.z_as_relative = true
```

**为什么这套架构成立**：所有部件共享同一帧表，第 n 帧的"身体姿态"在空间上是预先对好的。引擎不做任何骨骼变形，只是把同一时刻的图层逐层贴上——这就是"换衣服自动跟着动"的本质，也是冒险岛、RO 当年能做到几千套时装的原因。

### 4.5 换色：HSV 偏移 + 双通道遮罩

参考视频里踩的坑值得完整复现并解决：**做蓝皮肤角色时，脸变蓝了但手还是肉色**。原因是"肤色"被画在每个部件的独立像素里，只调头部就漏了手。

**方案对比**

| 方案 | 一致性问题 | AI 素材友好度 | 结论 |
|---|---|---|---|
| `self_modulate` 整体乘色 | 全部一起变暗，压不出干净色相 | 高 | 只用于整体明暗 |
| 索引色板替换（index map） | 完美 | 低（要美术产索引图） | 后期升级路径 |
| **HSV 偏移 + 遮罩通道** | 好，靠遮罩约束区域 | **高** | **本期采用** |

**遮罩规范**：每个部件可选一张同名 `_mask.png`，与主图同尺寸：

- `R` 通道 = 可染色强度（0=不染，255=全染）
- `G` 通道 = 皮肤区（1 表示这是皮肤像素）
- `B` 通道 = 预留（自发光/金属，未来做描边发光）

这样"脸"和"手"的皮肤像素都标 G=1，统一由 `skin_tint` 驱动，蓝皮肤角色自然脸手一致。

**Shader**（完整文件见 `shaders/part_tint.gdshader`）

```glsl
shader_type canvas_item;

uniform sampler2D tint_mask : filter_nearest, repeat_disable, hint_default_black;
uniform bool use_mask = false;

uniform float hue_shift : hint_range(-0.5, 0.5) = 0.0;
uniform float sat_mul : hint_range(0.0, 2.0) = 1.0;
uniform float val_mul : hint_range(0.0, 2.0) = 1.0;

uniform float skin_hue_shift : hint_range(-0.5, 0.5) = 0.0;
uniform float skin_sat_mul : hint_range(0.0, 2.0) = 1.0;
uniform float skin_val_mul : hint_range(0.0, 2.0) = 1.0;

varying vec4 v_modulate;

vec3 apply_hsv(vec3 c, float h, float s, float v) {
    vec3 hsv = rgb2hsv(c);
    hsv.x = fract(hsv.x + h);
    hsv.y = clamp(hsv.y * s, 0.0, 1.0);
    hsv.z = clamp(hsv.z * v, 0.0, 1.0);
    return hsv2rgb(hsv);
}

void vertex() {
    v_modulate = COLOR;   // 保留节点 modulate / 父级 modulate
}

void fragment() {
    vec4 base = texture(TEXTURE, UV);
    vec4 mk = use_mask ? texture(tint_mask, UV) : vec4(1.0, 0.0, 0.0, 1.0);

    vec3 c = apply_hsv(base.rgb, hue_shift, sat_mul, val_mul);

    // 皮肤区：单独一套参数，且不受 R 通道限制（皮肤可能不在可染区）
    vec3 skin = apply_hsv(base.rgb, skin_hue_shift, skin_sat_mul, skin_val_mul);
    c = mix(c, skin, mk.g);

    // 非可染区还原原色
    c = mix(base.rgb, c, mk.r);

    COLOR = vec4(c, base.a) * v_modulate;
}
```

**运行时设置**

```gdscript
func _make_material(part: PartDef, slot: StringName) -> ShaderMaterial:
    var m := ShaderMaterial.new()
    m.shader = preload("res://shaders/part_tint.gdshader")
    m.set_shader_parameter("use_mask", part.tint_mask != null)
    m.set_shader_parameter("tint_mask", part.tint_mask)
    _apply_tint(m, visual.tints.get(slot, Color(0.5, 1.0, 1.0)))
    return m
# Color 打包约定：r=hue_shift+0.5  g=sat_mul  b=val_mul
```

> 性能提示：`ShaderMaterial` 每个部件一份会破坏合批。优化见 §8.2——用 `instance uniform`（Godot 4.2+ 的 per-instance uniform）把参数下推到实例级，材质本身共享。

### 4.6 次级动画（头发/披风随风）

不要做物理骨骼（2D 精灵上没有骨骼，成本高且容易穿模）。用**顶点着色器按 UV.y 加权偏移**：

```glsl
// shaders/wind_sway.gdshader
shader_type canvas_item;

uniform float wind_strength : hint_range(0.0, 1.0) = 0.3;
uniform float wind_freq : hint_range(0.0, 8.0) = 1.8;
uniform vec2 wind_dir = vec2(1.0, 0.0);
uniform float sway_pivot_y : hint_range(0.0, 1.0) = 0.3;  // 固定端在画布上方

void vertex() {
    float w = clamp((UV.y - sway_pivot_y) / max(1.0 - sway_pivot_y, 0.001), 0.0, 1.0);
    w = w * w;                                  // 越靠末端摆动越大
    float phase = TIME * wind_freq + UV.x * 3.0; // 加 x 相位差，避免整体平移
    VERTEX += wind_dir * sin(phase) * w * wind_strength * 12.0;
}
```

`wind_strength` 由 `WeatherDirector` 广播（晴天 0.15 / 雨天 0.5 / 雪天 0.25），下雨时披风摆动幅度自然变大。

### 4.7 组合数计算与"丑组合"治理

**理论组合数**（对齐参考视频公式）

```
11 × 17 × 23 × 29 × 9 × 33 × 14 × 17 × 12 × … × 4(体型) ≈ 4.455e13
再乘每部件的 N 档颜色 → 组合数进入 e16 量级
```

但**能生成的组合 ≠ 该出现的组合**。参考视频自己也吐槽"大部分都长这样"。工程上必须做治理：

| 手段 | 实现 |
|---|---|
| 硬性互斥 | `PartDef.incompatible_with`，如"巨型翅膀 + 窄肩甲"直接不组合 |
| 标签分组 | 按 `tags` 分 theme（arcane / rustic / royal / undead），75% 概率只在同 theme 内组合 |
| 稀有度加权 | `weight` 控制随机分布，稀有件低概率出现，避免"满街神器" |
| 人工精选池 | 手工确认 200~300 套存入 `curated_outfits.tres`，重要 NPC 只从这里取 |
| 视觉回归截图 | CI 里批量生成 200 个随机角色截图人工过一遍，标注坏样本回灌黑名单 |

```gdscript
# core/outfit_randomizer.gd
func roll(rng: RandomNumberGenerator, theme: StringName = &"") -> CharacterVisual:
    var v := CharacterVisual.new()
    for slot in SLOT_ORDER:
        var pool := _filter(AssetDB.by_slot(slot), theme, v)
        if pool.is_empty():
            continue
        v.equipped[slot] = _weighted_pick(pool, rng)
        v.tints[slot] = _harmonize_color(rng)   # 同色系收敛，别随机出荧光撞色
    v.skin_tint = SKIN_PRESETS[rng.randi() % SKIN_PRESETS.size()]
    return v
```

> `_harmonize_color` 值得单独做：从一张 12 色的"角色主色卡"里抽 2 个邻近色，分配给衣服和披风，其余部件取中性色。这一个函数能消掉 80% 的"丑"。

## 5. 世界模拟

### 5.1 时间系统（一切模拟的基座）

```gdscript
# autoload/game_clock.gd
extends Node

signal minute_changed(total_minute: int)
signal hour_changed(hour: int)
signal day_changed(day: int)
signal season_changed(season: int)

const MIN_PER_DAY := 1440
const DAYS_PER_SEASON := 28

@export var real_seconds_per_game_day: float = 900.0  # 15 分钟 1 天

var total_minute: int = 6 * 60     # 从早上 6 点开始
var _acc: float = 0.0

func _process(delta: float) -> void:
    _acc += delta * (MIN_PER_DAY / real_seconds_per_game_day)
    if _acc < 1.0:
        return
    var step := int(_acc)
    _acc -= step
    _advance(step)

func _advance(minutes: int) -> void:
    var prev_hour := hour()
    var prev_day := day()
    total_minute += minutes
    if hour() != prev_hour:
        hour_changed.emit(hour())
    if day() != prev_day:
        day_changed.emit(day())
        if day() % DAYS_PER_SEASON == 0:
            season_changed.emit(season())

func hour() -> int: return (total_minute / 60) % 24
func minute() -> int: return total_minute % 60
func day() -> int: return total_minute / MIN_PER_DAY
func season() -> int: return (day() / DAYS_PER_SEASON) % 4
func time_of_day_01() -> float: return float(total_minute % MIN_PER_DAY) / MIN_PER_DAY
```

**设计要点**：`total_minute` 是唯一状态，其余全是从它派生的纯函数。存档只存一个 int，读档后所有系统靠重放信号恢复——极大降低存档复杂度。

### 5.2 昼夜

用 `GradientTexture1D` 存一天 24 小时的色调曲线，每帧采样：

```gdscript
# 5 个关键色：0点深蓝、5点紫、7点暖橙、12点中性、19点橙红、22点靛蓝
@export var day_gradient: Gradient
func _process(_d: float) -> void:
    var t: float = GameClock.time_of_day_01()
    canvas_modulate.color = day_gradient.sample(t).srgb_to_linear()
```

配合 `PointLight2D`（路灯、火把）与 `LightOccluder2D`（建筑轮廓）。夜间强化的不是"变暗"，而是**光比**：`canvas_modulate` 压到 0.35，再让光源提亮，画面才有夜晚的层次。

### 5.3 天气

状态机 + 权重表，切换时长 5~15 分钟游戏时间，避免高频抖动：

```gdscript
enum Weather { CLEAR, CLOUDY, RAIN, SNOW, STORM }

# 转移权重表：rows=当前, cols=下一个
const TRANSITIONS := {
    Weather.CLEAR:  {Weather.CLEAR: 0.55, Weather.CLOUDY: 0.35, Weather.RAIN: 0.10},
    Weather.RAIN:   {Weather.RAIN: 0.45, Weather.CLOUDY: 0.40, Weather.STORM: 0.15},
    Weather.SNOW:   {Weather.SNOW: 0.50, Weather.CLOUDY: 0.50},
```

天气输出一个 `EnvironmentParams` 结构，供其他系统消费：

| 参数 | 消费方 |
|---|---|
| `light_mul` | 昼夜控制器叠加 |

### 5.4 四季

### 5.5 环境互动（火 / 水 / 温度传播）

参考视频预告的"树着火、水结冰"，本质是**格子上的状态传播**。不要在每帧遍历全图。

```gdscript
# world/cells/cell_state.gd
class_name CellState
extends RefCounted

var wet: float = 0.0          # 0~1 含水量
var heat: float = 0.0         # 0~1 热量
var burning: float = 0.0      # 0~1 燃烧进度
var frozen: bool = false
var flammable: float = 0.0    # 由地块类型给出
```

```gdscript
# world/world_grid.gd
const TICK_HZ := 4.0          # 每秒 4 次，足够，省 CPU
var _active: Dictionary = {}   # Vector2i -> true，只有"活跃格"参与模拟

func _process(delta: float) -> void:
    _acc += delta
    if _acc < 1.0 / TICK_HZ:
        return
    _acc = 0.0
    var next_active := {}
    for cell_pos in _active.keys():
        _step_cell(cell_pos, next_active)
    _active = next_active

func ignite(pos: Vector2i) -> void:
    var c: CellState = get_cell(pos)
    if c == null or c.wet > 0.5:
        return
    c.burning = 0.01
    _activate(pos)                    # 只把着火点及其邻居加入活跃集

func _step_cell(pos: Vector2i, next_active: Dictionary) -> void:
    var c := get_cell(pos)
    if c == null: return
    # 燃烧：向邻居传播
    if c.burning > 0.0:
        c.burning += 0.35 / TICK_HZ
        if randf() < c.flammable * (1.0 - c.wet) * 0.6 / TICK_HZ:
            for n in NEIGHBORS:
                var nc := get_cell(pos + n)
                if nc and nc.burning == 0.0 and nc.flammable > 0.0:
                    ignite(pos + n)
        if c.burning >= 1.0:
            _char(pos)                # 变成焦黑地块，N 天后重生
    if c.burning > 0.0 or c.wet > 0.0 or c.frozen:
        _activate(pos, next_active)   # 保持活跃直到状态稳定
```

关键设计：**活跃集（active set）**。只有发生状态变化的格子及其邻居进入模拟队列，静止的草地不消耗任何 CPU。1000×1000 的地图，雨天全场湿润时活跃格也不过几千个。

结冰判定：`c.wet > 0.3 and (base_temp + weather.temperature_offset) < 0` → `frozen = true`，视觉上换一块冰面 tile + 碰撞改为滑行摩擦。

### 5.6 多阶段建筑

参考视频提到的"多阶段建筑"= 建造过程可视化。用**阶段数组**驱动，而不是 5 个独立预制体：

```gdscript
class_name Building
```

玩家敲一下加 `progress`，满了切下一阶段。**只有阶段切换才重建碰撞与视觉**，中间用 `progress` 驱动一个"逐渐显影"的 shader（`mix(transparent, opaque, progress)`），表现施工感。

## 6. 资产生产管线（纯 2D）

> **决策记录**：不引入 Blender。运行时零 3D，生产阶段也不用 3D。对齐不靠"同一骨架渲染"，改靠"同一张底图"。

### 6.1 不靠 3D，怎么保证对齐

3D 路线的对齐是**构造性**的：所有部件绑同一套骨架、过同一台相机，对齐是渲染的副产品。
纯 2D 路线要把这件事换成另一条等价约束：

> **先画一套标准姿势底图（Base Sheet），之后所有部件都是在这张底图上描出来的。**

底图是唯一真相源——它定义了每一帧、每个方向、每个关节落在画布的哪个像素上。部件只要贴着底图描，对齐就天然成立。等价性在于：**3D 用骨架约束所有部件，2D 用底图约束所有部件**，两者都是"先有一个基准，再让所有东西服从它"。

区别在于**违反约束的代价**：3D 里你不会画错位，因为渲染不给你这个机会；2D 里你可以随手画歪，系统不会拦你。所以纯 2D 必须靠**流程纪律 + 工具纠偏**来补这一环，见 §6.4。

### 6.2 标准底图（Base Sheet）—— 第一优先级，必须先锁死

这是整个项目最该先做、也最该谨慎对待的资产。

| 项 | 要求 |
|---|---|
| 内容 | body 的 4 动作 × 5 列（M1 阶段可先做 3 列） |
| 尺寸 | 与正式资产一致：256×256 画布，锚点 (128,216) |
| 关节标记 | 用高饱和色标出 8 个关节点：头顶、颈、肩L/R、肘L/R、髋、膝 |
| 产出 | `assets/base/base_sheet.png` + `base_joints.json`（关节点坐标） |
| 纪律 | 进 git，锁定后任何改动需评审；**改底图 = 全部部件返工** |

**画底图的正确顺序**（不要一上来就做行走动画）：

```
① S 正面站立（1 帧）→ ② W 侧面站立 → ③ N 背面站立
④ 由三张站立姿势推演 walk 8 帧 → ⑤ idle 4 帧 → ⑥ attack 6 帧 → ⑦ hurt 2 帧
```

先把三个静止姿势画到"自己满意且比例稳定"，再推演动作。**动作是静止姿势的插值，不是重新创作。** 这一步做扎实，后面 200 多个部件都省事；做潦草，后面每个部件都要返工。

**锁定后的铁律**：所有部件只允许"贴上去"，不允许改动身体比例。发现底图有问题要改，就停下所有部件生产，先改底图、再批量重对齐。

### 6.3 三种部件生产法（按成本从低到高）

| 方法 | 做法 | 适用 | 单件耗时 | 风险 |
|---|---|---|---|---|
| **A 复用改装** | 拿现有部件改色、改轮廓、加装饰 | 衣服/帽子/发型的变体 | 15~40 min | 低，最容易跑偏风格 |
| **B 底图描线** | 在底图上新建图层，沿底图轮廓描形、上色 | 新体型、新轮廓部件 | 1~3 h | 中，考验基本功 |
| **C AI 锁形生成** | 底图帧作 img2img 输入，低 denoise 只改材质 | 复杂材质（鳞甲、羽饰、蕾丝） | 0.5 h + 修 | **高，参数失控就废** |

**方法 C 的红线**（纯 2D + AI 路线唯一的技术底线）：

- `denoise` 必须控制在 **0.25~0.4**，并同时用底图做 ControlNet（lineart / canny）或 img2img 的初始图
- denoise 一旦超过 0.5，AI 就会**改形体**——它会自己"修正"姿势，于是这一帧就和相邻帧对不上了
- 生成后必须叠底图做 50% 不透明度对比，轮廓偏移超过 3px 直接弃用重生成
- **A/B 方法产出的部件是"人画准的"，C 方法产出的是"AI 画得像的"**，两者混用时要统一描边粗细与光源方向，否则一眼看出质感割裂

### 6.4 对齐工具箱（替代 Blender 那部分能力）

三个工具，缺一不可：

| 工具 | 作用 | 位置 |
|---|---|---|
| 底图叠加模板 | 画的时候看得见基准，防止凭感觉画歪 | Krita 模板层（正片叠底 30%） |
| `tools/align_parts.py` | 画完自动测偏移，给建议位移，可 `--apply` 修正 | 本仓库 |
| `tools/validate_assets.py` | 尺寸/列数/帧数/命名/空白帧/越界 | 本仓库 |

**`align_parts.py` 的实际能力边界（务必看清，别指望它救命）**

它的原理是：把新部件的 alpha 包围盒与 body 同帧的 alpha 包围盒做对比，按策略算偏移。

- 擅长：整体跑偏（比如整张图往下偏了 12px）、镜像方向漏画、列数错位
- **不擅长**：袖子比手臂宽、护手只覆盖半只手这类"包围盒本来就不该相等"的情况
- 结论：它是**纠偏工具，不是对齐工具**。真正的对齐只能靠底图描线这个动作本身

用法：

```bash
# 只看报告，不改文件
python tools/align_parts.py --base assets/base/base_sheet.png \
    --part assets/parts/clothes/clothes_mage_01_walk.png --anchor bottom

# 确认无误后直接平移修正，并输出合成预览
python tools/align_parts.py --base ... --part ... --anchor bottom --apply --preview out/
```

`--anchor` 三档：`bottom`（脚底对齐，用于 shoes/body）、`center`（包围盒中心，用于 hat/hair）、`none`（只报告，用于手套/武器）。

### 6.5 成本重算（按镜像后的真实帧数）

一帧 = 一个方向 × 一个动画帧。每变体帧数 = 20 帧（4+8+6+2）× 列数。

| 部件类 | 变体数 | 列数 | 帧数/变体 | 工时/变体 | 小计 |
|---|---|---|---|---|---|
| body（含底图） | 4 | 5 | 100 | 2.5 h | 10 h |
| head（头型） | 11 | 5 | 100 | 1.5 h | 16.5 h |
| hair（前后合计） | 34 | 5 | 100 | 1.2 h | 41 h |
| clothes | 29 | 5 | 100 | 2.0 h | 58 h |
| hat | 23 | 5 | 100 | 0.8 h | 18.4 h |
| weapon | 33 | 8 | 160 | 1.8 h | 59.4 h |
| 其余 10 槽 | ~80 | 5 | 100 | 0.8 h | 64 h |
| **合计** | **~234** | — | **≈23,400 帧** | — | **≈267 h** |

加上底图 25 h，总量 **≈290 h**。

对比几个关键数字：

- 8 方向不镜像 = 37,000 帧；5 列镜像 = 23,400 帧，**省 37%**
- 手工画 16 个完整角色（每角色 160 帧） = 2,560 帧，**但每个角色都不能复用**
- 纸娃娃 23,400 帧换 4.45e13 种组合

> **诚实的话**：对会画画的人，纯 2D 描底图比"建模+渲染+风格化+清理"更快；对不会画画的人，Blender 反而更快。选纯 2D 的前提是——**你能坐下来在底图上描 200 多个部件而不崩溃**。如果只是偶尔画两笔，M1 验证完就会知道自己该不该继续。

### 6.6 什么时候该回头上 3D（量化触发条件）

不要凭感觉，用三个信号判断：

| 信号 | 阈值 | 说明 |
|---|---|---|
| 对齐返工率 | 连续 20 个部件里 > 3 个需要重画 | 说明手工对齐已不可持续 |
| 非对称方向需求 | 8 方向 + 非对称部件占比 > 30% | 镜像通吃不了，帧数会暴涨 |
| 需要体型变化 | 出现"胖瘦/高矮/儿童体型"需求 | 2D 底图无法变形，只能整套重画，此时 3D 优势压倒性 |

任一触发再引入 Blender，**成本不浪费**：底图规范、帧表、锚点、校验脚本可以 1:1 复用到渲染流程，只是把"描"换成"渲"。这也是为什么 §4.1 的资产规范要先定死——它是两条路线共用的接口。

## 8. 性能预算

### 8.1 目标

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 帧率 | 60fps @1920×1080 | Godot 内置 Monitor |
| 同屏 NPC | 40（全部纸娃娃全层） | 压测场景 |
| 纸娃娃层数 | ≤20 层/角色 | 上限硬约束 |
| Draw Call | ≤120 | 依赖图集合批 |
| 单角色合成耗时 | <0.2ms/帧 | `Time.get_ticks_usec()` 打点 |

### 8.2 优化手段（按优先级）

1. **图集打包**：每个槽位的所有变体打进一张 2048² 图集（`AtlasTexture`）。40 角色 × 20 层 = 800 个 Sprite2D，若纹理只来自 6 张图集，合批后 draw call ≈ 个位数~十几。
2. **per-instance uniform**（Godot 4.2+）：换色参数下推到实例，`ShaderMaterial` 全局共享一份。否则 800 个材质直接让合批失效。
3. **远景烘焙**：距离 > 1200px 的 NPC，用 `SubViewport` 把当前帧合成一次，转成单张 `ImageTexture` 替代 20 层（只在换装/换动作时重烘）。这一步能把远处的渲染成本砍 90%。
4. **活跃集模拟**：见 §5.5，静止格子零成本。
5. **对象池**：NPC 进出视野不 `instantiate/free`，走池子复用。
6. **`_push_frame` 去重**：同一帧只在 `frame` 真正变化时赋值 `s.frame`，避免每帧 800 次属性写入。

### 8.3 已知性能陷阱

| 陷阱 | 症状 | 规避 |
|---|---|---|
| 每层一个 `AnimationPlayer` | 层级间动作不同步、CPU 高 | 单一时钟，见 §4.4 |
| 每帧 `SubViewport` 合成 | 帧率骤降到 20 | 只在换装时烘焙 |
| 每部件独立 `ShaderMaterial` | draw call 爆炸 | per-instance uniform |
| `Sprite2D.frame` 与 `hframes` 不匹配 | 花屏、显示错误帧 | 校验脚本强制 |
| 换季直接 `hue_rotate` 全屏 | 角色被染色 | 图集变体切换 |

**关键路径调整**：纯 2D 路线下，风险从"AI 出图一致性"前移到了"底图质量"。所以拆出 **M1-0 底图** 单独作为一关——底图不过关就绝不开工部件，否则 200 个部件会跟着一起返工。

M1 阶段只做 `body + head + clothes` 三个槽位、只画 3 列（S/W/N，E 用 W 镜像），先验证"同一帧表叠图"在你的美术风格下视觉成立。**这一步的 16 张图会直接告诉你：你适不适合走纯 2D。** 撑得住就继续，撑不住就按 §6.6 转 3D，此时你已经有底图和帧表，转过去也不浪费。

## 10. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| **手工对齐崩塌**（纯 2D 头号风险） | 高 | 致命 | 底图锁死 + `align_parts.py` 纠偏 + 每批 20 件抽检；返工率 >15% 即触发 §6.6 转 3D |
| AI 锁形失败（denoise 过高改了形体） | 高 | 高 | denoise 硬上限 0.4 + 轮廓偏移 >3px 弃用 |
| 底图返工导致全部部件重画 | 中 | 致命 | M1-0 单独成关，底图不过关不开工；底图改动走评审 |
| 部件接缝穿帮（脖子、手腕） | 高 | 中 | 统一在 body 层画出"连接处暗部"，让部件边缘留 2px 重叠 |
| 组合数大但丑的多 | 高 | 中 | §4.7 五重治理 + 人工精选池 |
| 20 层叠加导致 draw call 爆炸 | 中 | 高 | 图集 + per-instance uniform，M1 结束就做压测 |
| 火焰传播导致卡顿 | 中 | 中 | 活跃集 + 4Hz 低频 tick，M3 单独压测 500 棵同时燃烧 |
| 美术产能跟不上内容需求 | 中 | 中 | 部件优先级排序：先做"看得见的 6 槽"，其余槽位留灰 |
| 引擎版本升级破坏 API | 低 | 低 | 锁定 4.3.x，升级前跑全量回归 |

## 附录 A：资产工具

**A1 校验** `tools/validate_assets.py`，CI 中执行：

```bash
python tools/validate_assets.py assets/parts --anim-table anim_table.json
```

校验项：命名规范、画布尺寸、**列数（3/5/8）**、帧数匹配帧表、透明边距、锚点越界、空白帧、遮罩尺寸一致。

**A2 纠偏** `tools/align_parts.py`，画完部件后逐个检查偏移：

```bash
# 报告模式（不改文件）
python tools/align_parts.py --base assets/base/base_sheet.png \
    --part assets/parts/clothes/clothes_mage_01_walk.png \
    --anchor bottom --cols 5 --frames 8

# 修正模式（平移对齐 + 输出合成预览供肉眼复核）
python tools/align_parts.py --base assets/base/base_sheet.png \
    --part assets/parts/clothes/clothes_mage_01_walk.png \
    --anchor bottom --cols 5 --frames 8 --apply --preview preview/
```

输出示例：

```
[帧 S-0] body bbox=88,72,168,216  part bbox=86,68,170,212  Δ=(+0,-4)  -> 建议下移 4px
[帧 S-1] body bbox=88,72,168,216  part bbox=90,68,172,212  Δ=(+2,-4)  -> 建议下移 4px
汇总: 建议整体偏移 (0, +4)，最大帧间偏差 2px（可接受）
```

> 记住 §6.4 的定位：它是**纠偏**工具，只能发现"整体跑偏"，不能替你解决"袖子比手臂宽"。真正的对齐靠底图描线。
